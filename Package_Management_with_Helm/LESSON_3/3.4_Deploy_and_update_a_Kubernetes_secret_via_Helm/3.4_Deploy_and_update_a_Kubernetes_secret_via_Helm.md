# Deploy and Update a Kubernetes Secret via Helm

## Lesson overview

This lesson demonstrates how to add a Kubernetes Secret to an existing Helm chart, render the chart locally, deploy the change with `helm upgrade`, and verify the Secret in Kubernetes. Secrets are intended for sensitive values such as usernames, passwords, and SSH keys.

> **Security note:** Base64 is encoding, **not encryption**. Do not commit real credentials or rendered Secret values to source control. Kubernetes Secrets also require appropriate RBAC, and encryption at rest should be configured for stronger protection.

## Prerequisites

- A Kubernetes cluster with `kubectl` and Helm configured.
- An existing Helm chart named `first-chart` with a release named `first-chart` installed in the `default` namespace.
- The `templates/` directory from the previous ConfigMap exercise.

## Step 1: Create the Secret template

From the root of your `first-chart` chart, create `templates/secret.yaml`. The instructor copies a starter manifest from the course exercise files in folder `0304` (`secret_begin.yaml`). A simplified example is:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: first-secret
type: Opaque
data:
  username: YWRtaW4=
  password: <base64-encoded-example-password>
```

`YWRtaW4=` is the Base64 representation of the demonstration username `admin`. Replace the password placeholder with a Base64-encoded demonstration value before rendering or installing the chart.

## Step 2: Encode example credentials

On macOS or Linux, use:

```bash
printf %s 'admin' | base64
printf %s 'example-password' | base64
```

`printf` avoids adding a newline, just as `echo -n` does in the video. Copy the results into the Secret's `data` fields. On Windows PowerShell, an equivalent is:

```powershell
[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes('admin'))
[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes('example-password'))
```

For a simpler manifest, Kubernetes also supports `stringData`, which accepts plain strings and converts them to Secret data when submitted; however, plain values still need careful handling.

## Step 3: Preview the Helm templates

From the root of the chart, run:

```bash
helm template first-chart .
```

Confirm that the rendered output includes both the earlier ConfigMap and the new Secret. **Warning:** The rendered output contains encoded Secret values, so avoid sharing or logging it.

## Step 4: Deploy the Secret

Update the existing Helm release:

```bash
helm upgrade first-chart .
```

The instructor's example reports **revision 3**; your revision number may differ.

## Step 5: Verify the Secret

List Secrets in the default namespace:

```bash
kubectl get secrets
```

Inspect the Secret metadata and key sizes:

```bash
kubectl describe secret first-secret
```

In the demonstration, the Secret contains a `username` entry of **5 bytes** and a `password` entry of **13 bytes**. `kubectl describe secret` does not print the stored values.

## Command reference

| Command | Purpose |
|---|---|
| `helm template first-chart .` | Render chart templates locally without deploying. |
| `helm upgrade first-chart .` | Apply chart changes to an existing release. |
| `kubectl get secrets` | List Secrets in the current namespace. |
| `kubectl describe secret first-secret` | Inspect Secret metadata and data-key sizes without printing values. |
| `helm history first-chart` | View the release revision history. |

## Key takeaways

1. Kubernetes Secrets store sensitive configuration separately from application manifests.
2. Values under a Secret's `data` field must be Base64 encoded; Base64 alone does not secure them.
3. Place a Secret manifest in the Helm chart's `templates/` directory.
4. Use `helm template` to preview rendered resources and `helm upgrade` to apply changes.
5. Use `kubectl get secrets` and `kubectl describe secret` to verify creation without displaying Secret contents.
6. The next lesson covers rolling back a Helm release.
