# Helm: Using the `values.yaml` File

## Overview

The `helm create` command generates a `values.yaml` file containing default configuration values for a Helm chart. Helm templates can reference these values to customize Kubernetes resources without hardcoding configuration in files under `templates/`.

## 1. Purpose of `values.yaml`

- Stores the chart's default configuration.
- Supplies values to Kubernetes manifests rendered by Helm.
- Can be customized by adding, changing, or removing keys.
- Separates environment-specific settings from reusable templates.

## 2. Common Generated Settings

A newly generated `values.yaml` typically includes settings such as:

| Setting | Purpose |
|---|---|
| `replicaCount` | Number of application pod replicas |
| `image` | Container image repository, tag, and pull policy |
| `securityContext` | Container security settings |
| `resources` | CPU and memory requests and limits |
| `livenessProbe` | Checks whether a container should be restarted |
| `readinessProbe` | Checks whether a container is ready to receive traffic |
| `autoscaling` | Horizontal Pod Autoscaler configuration |

These are starting points, not required keys for every chart.

## 3. Add Custom Staging Values

For example, add this configuration to `values.yaml`:

```yaml
staging:
  sample: sample-12345
```

The original lesson uses staging configuration from its exercise files. The example above illustrates the same lookup and rendered value.

## 4. Access Values in a Helm Template

Helm uses Go template expressions enclosed in double curly braces:

```yaml
{{ .Values.staging.sample }}
```

| Expression | Meaning |
|---|---|
| `{{ ... }}` | Evaluates a Helm template expression |
| `.Values` | Accesses merged chart configuration values |
| `.staging` | Selects the `staging` mapping |
| `.sample` | Reads the `sample` key |

**Important:** Use `.Values` with a capital **V**. Helm template identifiers are case-sensitive; `.values` is not the correct built-in object.

## 5. Example: Use the Value in a ConfigMap

File: `templates/configmap.yaml`

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: first-chart-configmap
data:
  sample: {{ .Values.staging.sample | quote }}
```

With the example values above, Helm renders:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: first-chart-configmap
data:
  sample: "sample-12345"
```

The `quote` function ensures the ConfigMap data value is rendered as a string.

## 6. Preview and Deploy

Preview the generated YAML before applying it:

```bash
helm template first-chart .
```

Check the chart for common problems:

```bash
helm lint .
```

Upgrade an existing release:

```bash
helm upgrade first-chart .
```

Inspect the ConfigMap:

```bash
kubectl get configmap first-chart-configmap -o yaml
```

These commands assume you are in the chart directory, the release `first-chart` already exists, and you are using the correct Kubernetes namespace.

## 7. Overriding Defaults

A chart can use a separate environment-specific values file:

```bash
helm template first-chart . -f staging-values.yaml
```

You can also override a value from the command line:

```bash
helm template first-chart . --set staging.sample=sample-67890
```

Helm merges supplied values with chart defaults, with overrides taking precedence.

## Key Takeaways

1. `values.yaml` holds default, customizable chart configuration.
2. Helm's `helm create` command supplies example settings for pods, images, probes, resources, and autoscaling.
3. Add your own nested YAML keys for environments such as staging.
4. Access those keys using expressions such as `{{ .Values.staging.sample }}`.
5. Use `helm template` to preview the final Kubernetes YAML.
6. The next lesson introduces Helm conditional statements for dynamically controlling rendered Kubernetes resources.
