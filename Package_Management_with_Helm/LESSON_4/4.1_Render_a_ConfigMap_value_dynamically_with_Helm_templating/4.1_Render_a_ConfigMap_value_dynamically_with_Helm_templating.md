# Helm Templating: Render a ConfigMap Value Dynamically

## Summary

Helm's templating engine dynamically inserts values from chart metadata and configuration into Kubernetes manifests. This lesson uses `.Chart.Version` to append the chart version to a ConfigMap name, avoiding manual edits each time the version changes.

## 1. Why Use Helm Templating?

- Avoid hardcoded, frequently changing values.
- Reuse templates across chart versions and environments.
- Generate consistent Kubernetes YAML during installation and upgrades.

## 2. Chart Metadata

The `Chart.yaml` file stores metadata including the chart version:

```yaml
apiVersion: v2
name: first-chart
description: My first Helm chart
type: application
version: 0.1.0
appVersion: "1.0.0"
```

The `version` field is the **chart version**. It is different from `appVersion` and from a Helm release revision.

## 3. Template Syntax

```gotemplate
{{ .Chart.Version }}
```

- `{{ ... }}` marks a Helm Go-template expression.
- `.` refers to the current template context.
- `.Chart` accesses chart metadata.
- `.Version` selects the chart's version.

The names `Chart` and `Version` are case-sensitive.

## 4. Make the ConfigMap Name Dynamic

Before:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: first-chart-configmap
data:
  environment: development
  port: "8080"
```

After (`templates/configmap.yaml`):

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: first-chart-configmap-{{ .Chart.Version }}
data:
  environment: development
  port: "8080"
```

With `version: 0.1.0`, Helm renders the name as `first-chart-configmap-0.1.0`.

## 5. Preview and Upgrade

From the chart directory:

```bash
helm lint .
helm template first-chart .
helm upgrade first-chart .
kubectl get configmaps
```

Expected ConfigMap name:

```text
first-chart-configmap-0.1.0
```

The lesson shows the Helm release revision incrementing on each upgrade. A release revision is **not** the same as the version in `Chart.yaml`.

## 6. Change the Chart Version

Edit `Chart.yaml`:

```yaml
version: 0.1.1
```

Then run:

```bash
helm upgrade first-chart .
kubectl get configmaps
```

The newly rendered ConfigMap name is:

```text
first-chart-configmap-0.1.1
```

**Caution:** Renaming a ConfigMap changes its Kubernetes resource identity. On a normal Helm upgrade, the old resource is removed and the new one is created, unless special retention behavior applies. Any workloads that refer to the ConfigMap by name must also be updated. Versioning ConfigMap names is a teaching example, not a universal best practice.

## 7. Helpful Commands

| Command | Purpose |
|---|---|
| `helm template first-chart .` | Preview rendered YAML without installing |
| `helm lint .` | Check the chart for common issues |
| `helm upgrade first-chart .` | Upgrade an existing release |
| `helm list` | List installed releases |
| `helm history first-chart` | Inspect release revisions |
| `kubectl get configmaps` | List ConfigMaps in the current namespace |

## Key Takeaways

1. Helm templates replace hardcoded values with dynamic expressions.
2. `{{ .Chart.Version }}` reads the chart version from `Chart.yaml`.
3. Changing `Chart.yaml` and running `helm upgrade` re-renders the manifest.
4. Chart versions, application versions, and Helm release revisions serve different purposes.
5. The next lesson covers reading configuration values from `values.yaml`.
